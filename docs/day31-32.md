## 任务 1：学习 MHA / GQA / MQA（30 分钟）

### 三者的关系

```text
Query heads 数 Hq 不变，只改 KV heads 数 Hkv：

MHA   Hkv = Hq        每个 Query head 有专属的 K/V
GQA   1 < Hkv < Hq    每 Hq/Hkv 个 Query head 共享一组 K/V
MQA   Hkv = 1         所有 Query head 共享同一组 K/V
```

`Hq / Hkv` 就是 `num_key_value_groups`（Day 16 定义过的那个属性）。

```text
Hq=8, Hkv=2  →  groups=4
  Query head 0,1,2,3 → KV head 0
  Query head 4,5,6,7 → KV head 1
```

### 为什么 GQA 有效（论文的核心论点）

MQA（`Hkv=1`）省得最多，但**质量下降明显**——所有 head 被迫用同一套 K/V，
表达能力受限。MHA 质量最好但 Cache 最大。

GQA 是中间点，论文的发现是：**`Hkv=8` 左右几乎不损失质量，
但 Cache 已经降到 MHA 的 `Hkv/Hq`。** 这个性价比让它成为事实标准
（Llama-2 70B、Llama-3 全系、Mistral、Qwen 都用 GQA）。

### GQA 省的到底是什么（重要区分）

| | 省了多少 | 重要性 |
|---|---|---|
| **参数** | `2·D·Dh·(Hq - Hkv)`，8B 模型约 25M | 小，占比 0.3% |
| **KV Cache** | **降到 `Hkv/Hq`**，`32→8` 即 **1/4** | **巨大** |

**GQA 是显存优化，不是参数优化。** 这一点 Day 16 就强调过，
今天用真实数字确认（任务 5）。

注意 `Wq` 和 `Wo` **不变**（它们和 `Hq` 挂钩），
只有 `Wk`、`Wv` 从 `[D, Hq·Dh]` 缩到 `[D, Hkv·Dh]`。

## 任务 2：实现 KV head 共享（60 分钟）

### 两种实现方式

**方式 A：`repeat_kv`（HF 的做法）**

把 K/V 从 `[B, Hkv, S, Dh]` 复制成 `[B, Hq, S, Dh]`，然后走普通 MHA：

```python
def repeat_kv(x, n_rep):
    B, Hkv, S, Dh = x.shape
    if n_rep == 1:
        return x
    x = x[:, :, None, :, :].expand(B, Hkv, n_rep, S, Dh)
    return x.reshape(B, Hkv * n_rep, S, Dh)
```

**注意 `expand` 不复制内存**（返回 view），但紧跟的 `reshape`
因为要连续内存**会触发一次复制**。所以 `repeat_kv` 实际有拷贝开销。

**方式 B：`enable_gqa=True`（PyTorch SDPA 原生支持）**

```python
F.scaled_dot_product_attention(q, k, v, enable_gqa=True)
```

Q 是 `[B, Hq, S, Dh]`，K/V 是 `[B, Hkv, S, Dh]`，SDPA 内部处理共享，
**不实体化复制**。

### 两种方式的对比（今天值得实测的点）

| | `repeat_kv` | `enable_gqa` |
|---|---|---|
| 显存 | 多一份 `[B, Hq, S, Dh]` 的临时张量 | 无额外 |
| 兼容性 | 任何 attention 实现都能用 | 需要 PyTorch 2.5+ |
| 和 HF 一致 | 是 | 数值应该一致 |

**两种都实现**，用一个开关切换。这样：

- Day 19 的 HF parity 用 `repeat_kv`（和 HF 完全一致）
- Day 34 的 benchmark 可以对比两者的显存和速度差异

`n_rep = 1` 时提前返回是必要的优化——MHA 配置下不该有任何开销。

### 关键正确性要求：扩展顺序

这是六个必查错误的最后一条：**GQA 的 KV head 扩展方式错误**。

正确的扩展是**每个 KV head 连续重复 `n_rep` 次**：

```text
Hkv=2, n_rep=3  →  [k0, k0, k0, k1, k1, k1]     ✓ 正确
                   [k0, k1, k0, k1, k0, k1]     ✗ 错（交错）
```

因为 Query head 的分组是**连续的**（head 0~2 → KV 0，head 3~5 → KV 1）。
交错扩展会让每个 Query head 配到错误的 KV head。

**形状完全正确，不报错，结果全错。** 和 Day 9 Bug 2 同一类问题。

怎么保证写对：`x[:, :, None, :, :].expand(...).reshape(...)`
把 `n_rep` 插在 `Hkv` **之后**，reshape 时 `Hkv` 是高位、`n_rep` 是低位，
展开自然是连续重复。如果插在 `Hkv` 之前就会得到交错结果。

## 任务 3：GQA 测试 + 补 Day 30 遗留项（60 分钟）

`tests/test_attention.py` 新增：

1. **三种配置都能跑**：`Hkv=Hq`（MHA）、`Hkv=2`（GQA）、`Hkv=1`（MQA）
2. `Hq % Hkv != 0` 时构造报错（Day 16 已有，回归确认）
3. **`repeat_kv` 的扩展顺序**：用可区分的假数据
   （比如 `k[:, i, :, :] = i`）验证结果是 `[0,0,0,1,1,1]` 而非 `[0,1,0,1,0,1]`
4. **`Hkv=Hq` 时 `repeat_kv` 是恒等**（`n_rep=1` 提前返回）
5. **`repeat_kv` 与 `enable_gqa` 数值一致**
6. **`Hkv=1` 时，所有 Query head 看到的 K/V 相同**
   （手动构造，验证 attention 输出的对称性）
7. **与 HF 对齐**：`Hkv < Hq` 的配置下重跑 Day 19～20 的 parity 测试
8. Cache 的形状是 `[B, Hkv, S, Dh]` 而**不是** `[B, Hq, S, Dh]`

第 3 条直接针对那个必查错误，**用可区分的假数据是唯一可靠的验证方式**——
随机数据下交错和连续的结果都「看起来正常」。

第 8 条容易被忽略：**Cache 存的是 `Hkv` 份，不是 `Hq` 份**。
如果你在 `repeat_kv` **之后**才写 Cache，就白白存了 `Hq` 份，
GQA 的显存收益全部消失。

```text
正确顺序：投影 → RoPE → 写 Cache（Hkv 份）→ repeat_kv → attention
错误顺序：投影 → RoPE → repeat_kv → 写 Cache（Hq 份）← 收益归零
```

**这是 GQA 实现里最实质的一个坑**，比扩展顺序更容易犯。

## 任务 5：手算 KV Cache 显存矩阵（60 分钟）

### 公式

```text
KV bytes = 2 × L × B × S × Hkv × Dh × bytes_per_element
```

逐项确认来源，**不要背**：

| 因子 | 为什么 |
|---|---|
| `2` | K 和 V 两个张量 |
| `L` | 每层独立缓存（Day 26 的重点） |
| `B` | 每条序列独立 |
| `S` | 每个位置一份 |
| `Hkv` | **注意是 `Hkv` 不是 `Hq`**——GQA 的收益就在这 |
| `Dh` | 每个 head 的维度 |
| `bytes_per_element` | fp32=4, bf16/fp16=2, int8=1 |

### 三组计算（全部组合）

**1. 你的 2 层玩具模型**（`L=2, Hkv=4, Dh=32`，bf16）

先算这个，因为你能直接和 `sum(t.numel() * t.element_size() for t in cache.keys)` 对比。
**公式和实测必须一致**，不一致说明你对某个因子的理解有误。

**2. Llama-3 8B 级 GQA 模型**（`L=32, Hkv=8, Dh=128`，bf16）

我已经验证过下面的数字，你自己算完再核对：

| batch | context | GQA (`Hkv=8`) | 若用 MHA (`Hkv=32`) | GQA 收益 |
|---|---|---|---|---|
| 1 | 2K | 0.25 GiB | 1.00 GiB | 4× |
| 1 | 8K | **1.00 GiB** | 4.00 GiB | 4× |
| 1 | 32K | 4.00 GiB | 16.00 GiB | 4× |
| 16 | 8K | **16.00 GiB** | 64.00 GiB | 4× |

**3. 和模型权重对比**（这是今天最重要的结论）

Llama-3 8B 的权重在 bf16 下约 **15 GiB**（8.03B × 2 字节）。

```text
B=1,  S=8K   → KV Cache  1 GiB  =  权重的  7%
B=16, S=8K   → KV Cache 16 GiB  =  权重的 107%   ← 超过权重本身
```

**KV Cache 会超过模型权重。** 这是现代 LLM 推理服务最核心的显存约束，
也是 vLLM 那类系统存在的全部理由——它们的核心工作就是**把 KV Cache 管好**。

### 写成脚本

`benchmarks/bench_cache_memory.py`：

- 一个纯计算函数 `kv_cache_bytes(L, B, S, Hkv, Dh, dtype)`
- 打印上面三组表格
- **一个与实测对比的断言**：玩具模型上公式值 == 实际 Cache 占用

最后一条把公式和代码闭环了，别省。

### 顺手推一个有用的量

**「每个 token 的 KV 成本」**：

```text
per_token_bytes = 2 × L × Hkv × Dh × bytes
```

Llama-3 8B bf16：`2 × 32 × 8 × 128 × 2 = 131072` 字节 = **128 KiB / token**。

这个数字非常实用：给定剩余显存，直接除一下就知道还能缓存多少 token。
比如剩 10 GiB → `10 × 1024 / 128 ≈ 80000` 个 token 的额度，
可以是 1 条 80K 的序列，也可以是 10 条 8K 的序列。

**这正是 vLLM 里 KV block 调度的基本算术。** 写进笔记。

## 今日最重要的面试式问题

**GQA 为什么能减少 KV Cache？减少多少？**

因为 KV Cache 的大小和 **`Hkv`** 成正比：

```text
2 × L × B × S × Hkv × Dh × bytes
```

GQA 让多个 Query head 共享一组 K/V，`Hkv` 从 `Hq` 降到几个。
Llama-3 8B 的 `Hq=32, Hkv=8`，Cache **直接变成 1/4**：
8K context 下从 4 GiB 降到 1 GiB。

注意它**省的不是参数**——参数只省了 `Wk`/`Wv` 的一部分，8B 模型约 25M，占比 0.3%。
**GQA 是显存优化。**

追问：**实现 GQA 时最容易犯的错是什么？**

**在 `repeat_kv` 之后才写 KV Cache。** 这样缓存里存的是 `Hq` 份而不是 `Hkv` 份，
GQA 的显存收益**全部消失**，而且所有测试都会通过（数值完全正确）。

正确顺序是：投影 → RoPE → **写 Cache（`Hkv` 份）** → `repeat_kv` → attention。

第二个坑是扩展顺序：必须是 `[k0,k0,k0,k1,k1,k1]` 而不是 `[k0,k1,k0,k1,k0,k1]`，
因为 Query head 的分组是连续的。这个错误形状完全正确、不报错、结果全错，
只能用可区分的假数据测出来。
