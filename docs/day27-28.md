## 任务 1：学习 HF 三种 Cache（30 分钟）

| 类型 | 数据结构 | 更新方式 | 适用 |
|---|---|---|---|
| **DynamicCache** | 每层一对 `[B,Hkv,S,Dh]`，`S` 随生成增长 | `torch.cat` | 默认；长度未知时 |
| **StaticCache** | 每层一对 `[B,Hkv,max_S,Dh]`，一次分配 | 按位置**原地写入** | 需要 `torch.compile` / CUDA Graph |
| **QuantizedCache** | K/V 以 int8 / int4 存 | 量化后写入 | 显存吃紧、长上下文 |

**为什么 `StaticCache` 是 `torch.compile` 的前提**：
`DynamicCache` 每轮的张量形状都变（`S` → `S+1`），
会让 `torch.compile` 反复重新编译（recompilation），性能反而更差。
形状固定的 `StaticCache` 才能编译一次复用。Day 38 会实测这个。

`QuantizedCache` 我们不实现，但要知道它的动机：
从 Day 16 那个公式看，KV Cache 和 `bytes_per_element` 成正比，
bf16 → int8 直接砍一半。代价是精度损失。

在 HF 源码里瞄一眼 `cache_utils.py` 的 `DynamicCache.update()` 签名，
确认它接收 `(key_states, value_states, layer_idx, cache_kwargs)`——
**`layer_idx` 就是 Day 20 反向定位练习里那个问题的答案。**

## 任务 2：实现 `DynamicCache`（70 分钟）

### 数据结构

```python
class DynamicCache:
    def __init__(self, num_layers: int):
        self.keys:   list[torch.Tensor | None] = [None] * num_layers
        self.values: list[torch.Tensor | None] = [None] * num_layers
```

用 `None` 表示「这一层还没写过」，比用空张量简单
（空张量还要构造正确的 `[B,Hkv,0,Dh]` 形状）。

### 核心方法

```text
update(layer_idx, new_k, new_v) -> (full_k, full_v)
get_seq_length(layer_idx=0)     -> int
```

`update` 的逻辑：

```python
if self.keys[layer_idx] is None:
    self.keys[layer_idx] = new_k
else:
    self.keys[layer_idx] = torch.cat([self.keys[layer_idx], new_k], dim=-2)
return self.keys[layer_idx], self.values[layer_idx]
```

### `dim=-2` —— 今天最容易写错的一个数字

K 的形状是 `[B, Hkv, S, Dh]`：

| 维度 | 索引 | 含义 | 拼错的后果 |
|---|---|---|---|
| `B` | 0 | batch | batch 变大，形状不匹配后续会报错 |
| `Hkv` | 1 | KV head | **head 数变多**，`repeat_kv` 和 attention 全乱 |
| `S` | **-2** | **sequence** ← 正确 | — |
| `Dh` | -1 | head 维度 | **维度变长**，`sqrt(Dh)` 和后续投影全错 |

用 `dim=-2` 而不是 `dim=2`：这样 `[B,Hkv,S,Dh]` 和 `[Hkv,S,Dh]`
（万一某处少了 batch 维）都能对。防御性写法。

**加一条断言**，让写错立刻炸：

```python
assert new_k.shape[:2] == past_k.shape[:2], \
    f"batch/head 维不匹配：past {tuple(past_k.shape)} vs new {tuple(new_k.shape)}"
assert new_k.shape[-1] == past_k.shape[-1], \
    f"head_dim 不匹配：past {past_k.shape[-1]} vs new {new_k.shape[-1]}"
```

拼接前检查「除了 sequence 维之外全都一致」。这两行能挡住绝大多数拼错维度的情况。

## 任务 3：改造 attention 支持 cache（60 分钟）

### 签名变化

```text
forward(hidden_states, position_ids, attn_mask=None,
        cache=None, layer_idx=None) -> hidden_states
```

内部流程（注意 RoPE 和 cache 的顺序）：

```text
1. 投影得到 Q, K, V             [B, H*, Sq, Dh]
2. 对 Q, K 应用 RoPE            ← 用本轮的 position_ids
3. cache.update(layer_idx, K, V) → full_K, full_V   [B, Hkv, Skv, Dh]
4. attention(Q, full_K, full_V, mask)
```

### 第 2 步和第 3 步的顺序至关重要

**RoPE 必须在写入 Cache 之前应用。**

原因：缓存的应该是**已经带好位置信息**的 K。如果先缓存再旋转，
每轮都要对全部历史 K 重新旋转一遍——那就白缓存了，而且位置会被叠加旋转，结果完全错。

HF 的 `LlamaAttention` 也是这个顺序（Day 10 观察过：
`apply_rotary_pos_emb` 在 `past_key_value.update` 之前）。

> **注意 V 不做 RoPE**（Day 13 的结论），所以 V 缓存前后无区别。

### 三处必须传对的东西

| 传什么 | Prefill 时 | Decode 时 | 传错的后果 |
|---|---|---|---|
| `position_ids` | `[0..S-1]` | **`[S+t]`**（绝对位置） | 传 0 → 模型把新 token 当句首 |
| mask 的 `Sq/Skv` | `S/S` | **`1/(S+t+1)`** | 用 `tril` → 只看见第 0 个 key |
| `layer_idx` | 每层不同 | 每层不同 | 传错 → 读到别层的 Cache |

`layer_idx` 建议在 `Block.__init__` 里存成 `self.layer_idx`，
由 `model.py` 在构造时传入——不要每轮从外面传，容易错。

## 任务 4：设计 `prefill` / `decode` API（50 分钟）

### 两个函数

```text
prefill(input_ids [B,S], attention_mask [B,S])
    -> (logits [B,V], cache)          # 只返回最后一位的 logits

decode(next_token_ids [B,1], cache, cache_position [B] 或 int)
    -> (logits [B,V], cache)
```

### 为什么要分成两个函数

要求是「Prefill 可多 token，Decode 通常单 token」。
分开的价值不只是清晰：

1. **形状假设不同**：`prefill` 的 `Sq=S`，`decode` 的 `Sq=1`。
   分开写可以各自加严格的形状断言。
2. **mask 构造不同**：`prefill` 要 `tril`，`decode` 要全可见的一行。
3. **优化路径不同**：`prefill` 需要全量 GEMM，`decode` 走小 GEMM。
   第 4 周的 benchmark 会分别测这两条路径——**接口分开才好测**。
4. **`prefill` 只需要最后一位的 logits**（Day 3 的 1024 倍优化），
   `decode` 天然只有一位。

### `cache_position` 的语义

这是今天最需要想清楚的一个量：**新 token 在完整序列里的绝对位置**。

```text
prompt 长度 3，已生成 2 个 token
→ 下一个 token 的 cache_position = 5
→ 它同时是：RoPE 的 position、Cache 的写入下标
```

**RoPE position 和 Cache 写入位置是同一个数**——这是设计上的关键简化，
用一个变量同时驱动两处，就不会出现「位置对了但写错格子」的情况。

### batch 里长度不齐时怎么办

Day 23 已经处理过：每条序列的真实长度不同，
所以 `cache_position` 是 `[B]` 的张量，不是标量。

但**Cache 的写入位置**又必须一致（否则 `[B,Hkv,S,Dh]` 里每条序列的有效区间不同）。
Left padding 正好解决这个：

```text
[P, P, a, b, c]  → 有效数据靠右，Cache 里的位置也靠右
```

所有序列的 Cache 都写到同一个下标，只是前面几格是 PAD 的 K/V。
**PAD 的 K/V 会被 attention mask 屏蔽**，所以不影响结果——
这就是「Padding token 被写入有效 Cache」那条错误的正解：
**允许写入，但必须保证 mask 屏蔽它。**

> RoPE 的 position 仍然按 `cumsum` 规则算（Day 23），
> 和 Cache 下标可以不同。这是长度不齐时唯一需要区分的地方。

### 改造 `generate`

```text
logits, cache = prefill(input_ids, attention_mask)
next_token = sample(logits)
for step in range(max_new_tokens - 1):
    logits, cache = decode(next_token, cache, cache_position)
    next_token = sample(logits)
    cache_position += 1
```

**循环里不再有 `input_ids` 的拼接**（只为最终输出保留一份记录）。
这就是本周门禁那句「Prefill 后每轮 Decode 只输入新 token」。

## 今日最重要的面试式问题

**RoPE 应该在写入 KV Cache 之前还是之后应用？为什么？**

**之前。** 缓存的必须是**已带位置信息**的 K。

如果先缓存原始 K、每轮再对全部历史重新旋转，那么：
① 白缓存了（每轮还是要处理全部历史），
② 更糟的是位置会被**叠加旋转**——第 `t` 轮时历史 K 已经被转过 `t-1` 次，结果完全错。

HF 的 `LlamaAttention` 也是这个顺序：`apply_rotary_pos_emb` 在 `cache.update` 之前。
顺带说，V 不做 RoPE，所以 V 的顺序无所谓。

追问：**K/V 应该在哪个维度拼接？**

`dim=-2`，即 sequence 维（`[B, Hkv, S, Dh]` 的第 3 维）。

拼错的后果各不相同：拼 `dim=1` 会让 head 数变多，
拼 `dim=-1` 会让 `head_dim` 变长——两者都可能在形状上「看起来能跑」，
所以要加断言检查「除 sequence 维外其余维度一致」。

再追问：**Decode 时 `cache_position` 是什么，为什么它同时驱动两处？**

它是新 token 在完整序列里的**绝对位置**。
既是 RoPE 的旋转角度依据，又是 Cache 的写入下标。

用一个变量驱动两处是有意的设计——避免出现「RoPE 位置对了但 Cache 写错格子」
这种两个变量不同步的 bug。
