## 关于顺序的说明

今天**跳过** Positional Embedding 和 Attention，直接从 embedding 接到出口再接成循环。

这是刻意的：先用最少的零件打通一条端到端能跑的链路，后面每加一层都能立刻验证「输出还对不对」。
如果先堆 attention，要等很久才能看到第一个 token 被生成出来。

代价是这个模型现在**没有位置概念、也没有上下文交互**：

- Token Embedding 查不出位置（Day 01～02 已验证）
- 没有 Attention，位置 `i` 的 hidden state 完全不受其他位置影响

所以今天生成出来的 token 序列**毫无意义**，而且大概率会立刻陷入重复。
这不是 bug，是预期行为——今天验证的是**管道通不通**，不是**输出好不好**。

欠着的债记在这里别忘：

- [ ] Positional Embedding（学习单元 Day 14，RoPE）
- [ ] Attention（学习单元 Day 6～9）

## 任务 1：学习 LM Head 与 logits（25 分钟）

必读：[PyTorch `nn.Linear`](https://docs.pytorch.org/docs/stable/generated/torch.nn.Linear.html)

只需要搞明白：

1. LM Head 就是一个 `nn.Linear(D, V)`：把每个位置的 D 维向量，映射成词表上 V 个分数
2. 形状怎么变：`[B, S, D]` → `[B, S, V]`
3. logits 是**未归一化的分数**：可以是负数、可以大于 1、加起来不等于 1
4. softmax 做了什么，以及**什么时候才真的需要它**
5. `argmax(logits)` 和 `argmax(softmax(logits))` 是什么关系
6. 为什么 GPT-2 的 lm_head 是 `bias=False`
7. `nn.Linear(D, V)` 的 `weight` 形状为什么是 `[V, D]` 而不是 `[D, V]`

第 7 条是任务 5 weight tying 的伏笔，别跳过。

**不要深入**采样策略（top-k / top-p / beam search）和训练损失函数——那是学习单元 Day 22。

笔记见 [`concepts/02-lm-head.md`](./concepts/02-lm-head.md)，已写好，直接读。

## 任务 2：logits 与 softmax 实验（30 分钟）

新建 `notebooks/day03_logits_and_softmax.ipynb`，沿用
`day01_tokenizer_playground.ipynb` 的风格：每个实验一个 markdown + 一个 code cell。

`LMHead` 要到任务 3 才实现，所以这里先用 `torch.randn` 造假 logits——
softmax 的性质跟 `LMHead` 写得对不对无关，用随机数反而更干净。

四个实验：

1. **logits 不是概率**：打印 min / max / sum，确认有负数、和不等于 1
2. **softmax 之后才是**：确认全部落在 `[0, 1]` 且每行和为 1
3. **argmax 不变**：验证 `logits.argmax(-1)` 和 `softmax(logits).argmax(-1)` 完全相同
4. **温度**：对 `logits / T` 做 softmax，比较 `T=0.5 / 1.0 / 2.0` 的分布尖锐程度

**关键结论：** softmax 是单调变换，不改变排序。
所以贪心解码（只要最大的那个）根本不需要算 softmax；
只有要**概率值**（采样、算困惑度、看置信度）时才需要。

在 GPT-2 尺度上，每步对 50257 个数做一次 softmax 是纯浪费。

## 任务 4：`TinyLM`，预测下一个 token（30 分钟）

在 `src/mini_transformer/tiny_lm.py` 里把两块拼起来：

```text
TinyLM = TokenEmbedding + LMHead

forward(input_ids [B, S]) -> logits [B, S, V]
predict_next_token(input_ids [B, S]) -> next_ids [B]
```

`predict_next_token` 取 `logits[:, -1, :]` 得到 `[B, V]`，再 argmax 得到 `[B]`。

**动手前先想清楚这两个问题**：

- 为什么只要最后一个位置？前面 S-1 个位置的 logits 是干什么用的？
- 因果语言模型里，位置 `i` 的 logits 预测的是哪个位置的 token？

想明白之后，再想第三个——这是今天最有价值的一点：

> 既然解码时只用最后一个位置，那 `[B, S, D] @ [D, V]` 这个矩阵乘
> 是不是**从一开始就只该算最后一行**？

在 GPT-2 尺度上这两者差距是：

```text
预填充 [1, 1024, 768] @ [768, 50257] = 79.0   GFLOP
解码   [1,    1, 768] @ [768, 50257] =  0.077 GFLOP   ← 差 1024 倍
```

先算完整个 `[B, S, V]` 再切片，等于白做 1024 倍的计算。
所以 `LMHead` 要留一条只处理最后一位的路径。

## 任务 5：Weight tying 与参数量对比（25 分钟）

给 `TinyLM` 加一个 `tie_weights()`，让 `lm_head` 和 `embedding` 共享**同一个张量**。

为什么能直接共享、不用转置：两者权重形状本来就一样。

```text
nn.Embedding(V, D).weight   -> [50257, 768]
nn.Linear(D, V).weight      -> [50257, 768]
```

验证与对比：

1. 用 `is` 确认两个 `weight` 是同一个对象，不只是数值相等
2. 改动其中一个，另一个跟着变
3. 统计参数量，在 GPT-2 尺度上对比

```text
untied  两份权重  77.2M 参数  fp32 294 MB
tied    一份权重  38.6M 参数  fp32 147 MB
省下 38.6M —— GPT-2 small 全模型才 124M
```

`GPT2Config().tie_word_embeddings` 是 `True`，GPT-2 确实这么做。

**想清楚为什么这么做是合理的**：`hidden @ W.T` 的第 `i` 个分数，
就是 hidden 向量和「token i 的 embedding 向量」的点积。
所以 LM Head 在问的是「当前状态和哪个 token 的向量最像」——
用同一张表既合理又省一半参数。

## 任务 6：学习自回归生成与停止条件（20 分钟）

必读：[HF Generation Strategies](https://huggingface.co/docs/transformers/main/generation_strategies)

**只看 greedy 那一节。** temperature / top-k / top-p 是学习单元 Day 22，今天不要碰。

要搞明白的：

1. 为什么 LLM 必须**逐个** token 生成，不能一次吐出整句
2. 一轮生成的完整动作序列是什么
3. 两种停止条件：`max_new_tokens` 到顶，和生成出 EOS
4. 生成的 token 要**拼回输入**，成为下一轮的上下文

第 1 条的答案是今天的核心：第 `t` 个 token 的概率分布依赖前 `t-1` 个 token，
而第 `t-1` 个 token 是上一轮才产生的。**依赖链是串行的，无法并行展开。**

这也是推理和训练的根本差异：训练时整句真实 token 已知，一次前向就能算完所有位置
（teacher forcing）；推理时后面的 token 还不存在，只能一个一个来。

笔记落到 `docs/concepts/03-autoregressive-loop.md`（今天新建）。

## 任务 7：实现无 KV Cache 的 `generate`（30 分钟）

在 `src/mini_transformer/generate.py` 里实现最朴素的贪心生成。骨架：

```python
for _ in range(max_new_tokens):
    logits = model(input_ids)
    next_token = logits[:, -1].argmax(dim=-1, keepdim=True)
    input_ids = torch.cat([input_ids, next_token], dim=1)
```

**照抄这段之前，先自己写一遍再对照。** 然后补上骨架里没写的东西：

- `torch.inference_mode()` 包起来——推理不需要梯度
- `max_new_tokens` 之外加 EOS 停止（先支持 `eos_token_id=None` 表示不启用）
- batch 里每条序列**独立**的 finished 状态：某条先生成 EOS，它后面的位置不该再算作有效输出

最后一条是本任务真正的难点。batch 里各条序列不会同时结束，
而循环是整批一起推进的。想清楚：先结束的那条，后续轮次要怎么处理？

> 提示：这一版**不要求**做得完美。「每条序列独立 finished 状态」正式排在
> 学习单元 Day 21。今天只要能识别出这个问题、并留下注释说明当前版本的局限就够了。

**明确不做**：KV Cache（学习单元 Day 26～30）、采样（Day 22）、
left padding 处理（Day 23）。今天的目标是一个**能跑但很慢**的正确 baseline。

## 任务 8：量化重复计算的浪费（20 分钟）

这是 Day 4 最重要的产出。新建 `notebooks/day04_autoregressive_waste.ipynb`。

在循环里打印每轮的 `input_ids.shape[1]`，你会看到它单调递增：

```text
第 1 轮 forward 10 个 token → 产出第 11 个
第 2 轮 forward 11 个 token → 产出第 12 个   ← 前 10 个又算了一遍
第 3 轮 forward 12 个 token → 产出第 13 个   ← 前 11 个又算了一遍
```

**前面的 token 每一轮都被重新计算了一次，而它们的结果每轮都完全相同。**

累加一下总共处理了多少 token-位置，和「理想情况」对比：

| prompt 长度 | 生成数 | 无 Cache 累计 | 有 Cache 累计 | 倍数 |
|---|---|---|---|---|
| 10 | 20 | 390 | 29 | 13.4× |
| 1024 | 100 | 107,350 | 1,123 | 95.6× |

自己动手算一遍这两行，别只是读。公式是 `Σ(P .. P+N-1)` 对 `P + (N-1)`。

**这个浪费就是 KV Cache 存在的全部理由。** 现在把它测出来、记下来，
到学习单元 Day 26～30 实现 Cache 时，你会有一个明确的 baseline 可以对比。

注意今天这个模型**没有 Attention**，所以严格来说重复计算的只是 embedding 查表和一个 GEMM。
等 Attention 加上之后，浪费会更严重（Attention 中间矩阵随 S² 增长）。

两种输入形状走不同的 BLAS 归约顺序，GPT-2 尺度实测差到 ~3e-6，
而小配置下又恰好逐比特相等。写成 `torch.equal` 会得到一个「本地绿、换 shape 红」的测试。

## 今日最重要的面试式问题

**生成第 101 个 token 时，LM Head 需要对多少个位置做矩阵乘？**

答案必须是：**1 个**。

只有最后一个位置的 logits 会被用来预测下一个 token，前面 100 个位置的 logits 在推理阶段
计算了也是丢掉。训练时不一样——teacher forcing 下每个位置的 logits 都要参与算 loss。

**推理和训练在这里的行为不同**，这是很多人第一次写推理引擎时白白浪费算力的地方。

追问（Day 4 的部分）：**那前面 100 个位置的 hidden state 需要重算吗？**

不需要——它们每轮的结果完全相同。但今天这版 baseline **确实在重算**，
这就是 KV Cache 要解决的问题。
