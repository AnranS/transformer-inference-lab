## 任务 1：学习 CUDA 异步语义（40 分钟）

昨天已经知道「要 synchronize」，今天搞清**为什么**以及**什么时候会隐式同步**。

### 执行模型

```text
CPU（Python）          GPU
─────────────────────────────────────
model(x) 调用      →   kernel 入队
立刻返回                kernel 执行中...
下一行 Python 继续      ...
                        ...
```

CPU 只负责**提交任务**，不等待完成。这让 CPU 能提前提交后续 kernel，
GPU 不会因为等 Python 而空闲——这是 GPU 高利用率的基础。

### 什么操作会隐式同步（重要）

不是所有代码都需要显式 `synchronize`。这些操作会**自动等待**：

| 操作 | 为什么会同步 |
|---|---|
| `tensor.item()` | 要把值取到 Python，必须等算完 |
| `tensor.cpu()` / `.numpy()` | 要拷回主机内存 |
| `print(tensor)` | 内部要读取值 |
| `int(tensor)` / `float(tensor)` | 同 `item()` |
| `tensor.min()` 后取值 | Day 2 踩过这个（`TokenEmbedding` 的范围检查） |
| `if tensor > 0:` | 要得到布尔值 |

**这解释了 Day 2 那个发现**：`token_ids.min()` 在解码热路径上有明显开销——
它强制了一次 GPU→CPU 同步，让流水线断掉。当时我们做成了可关闭的开关，
现在知道了完整原因。

**推论：生成循环里不要有 `.item()`。** 比如
`if finished.all().item(): break` 每轮都会同步一次。
真实推理引擎会把停止判断也放在 GPU 上，或者每 N 步才检查一次。

### 显存统计的三个量

| 函数 | 含义 |
|---|---|
| `memory_allocated()` | **当前**张量实际占用 |
| `max_memory_allocated()` | **峰值**张量占用 |
| `memory_reserved()` | PyTorch 从驱动**预留**的总量（缓存池） |

`reserved >= allocated`。差值是 PyTorch 的缓存池——
它不还给驱动，为了下次分配更快。

**所以 `nvidia-smi` 显示的数字总是大于 `memory_allocated()`**，
两者不矛盾。报告显存时要说清用的是哪一个。Day 36 会详细做。

## 任务 2：Decode benchmark（60 分钟）

`benchmarks/bench_decode.py`。Notion 指定两组扫描：

| 组 | 固定 | 变化 |
|---|---|---|
| A | batch | context 长度：128, 512, 1024, 2048, 4096 |
| B | context | batch：1, 2, 4, 8, 16, 32 |

**测量单位是「一个 decode 步」**，不是整个生成过程。做法：
先 prefill 到目标 context 长度，然后测单步 `decode()` 的时间。

记录：单 token latency（ms）、tokens/s（`batch / latency`）、峰值显存。

### 先写预测

| 预测 | 理由 |
|---|---|
| A 组：latency 随 context **缓慢**增长 | 权重读取量固定，只有 Cache 读取量随 context 增长 |
| B 组：latency 随 batch **几乎不变**（小 batch 区间） | 访存密集，权重被整个 batch 共享 |
| B 组：tokens/s 随 batch **近似线性上升** | 上一条的直接推论 |
| Decode 的单步时间 << Prefill 的单 token 时间 | Decode 只算 1 个位置 |

**B 组那两条是今天最重要的验证。** 如果 tokens/s 真的随 batch 线性上升，
就证明了 Day 26 那个论断：Decode 阶段增大 batch 几乎免费。

这也是**为什么所有推理服务都做 continuous batching**——
把并发请求凑成大 batch，吞吐几乎线性提升而延迟不变。

### A 组会在哪里转折

context 很小时，时间被**权重读取**支配（固定成本），latency 几乎不变。
context 足够大后，**Cache 读取**超过权重读取，latency 开始明显增长。

用 Day 31～32 的数字估转折点：Llama-3 8B 单层权重约 218M 参数 × 2 字节 = 436 MB，
每 token 的 KV 是 128 KiB。所以约 `436MB / 128KiB ≈ 3400` 个 token 时
两者相当——**理论转折点在 3～4K context**。

你的小配置上转折点不同，自己算一遍再和实测对比。**这个对照很能说明你是否真的理解了。**

## 任务 3：MHA / GQA / MQA 对比（40 分钟）

同一个 `Hq`，三种 `Hkv` 配置，在**长 context**（比如 4096）下对比：

| 配置 | KV Cache 大小 | 预期 decode latency |
|---|---|---|
| MHA `Hkv=Hq` | 基准 | 最慢（读最多 Cache） |
| GQA `Hkv=Hq/4` | 1/4 | 明显更快 |
| MQA `Hkv=1` | `1/Hq` | 最快 |

**关键：差异要在长 context 下才明显。** 短 context 时 Cache 读取
不是瓶颈（被权重读取掩盖），三者差不多。

这一条实测能同时验证两件事：Day 31 的「GQA 是显存优化」，
以及「Decode 是访存密集」——**Cache 变小直接让 Decode 变快，
这只有在访存受限时才成立。**

如果你在 CPU 上测不出明显差异，是正常的（CPU 的算力/带宽比不同）。
记下来，等有 GPU 时重测。

## 任务 4：学习 Profiler（30 分钟）

```python
from torch.profiler import profile, ProfilerActivity

with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             record_shapes=True) as prof:
    model(x)
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=20))
```

三个关键点：

1. **`record_shapes=True`** —— 能看到每个算子的输入形状。
   区分「大 GEMM」和「小 GEMM」全靠这个。
2. **`sort_by`** —— `"cuda_time_total"` 看 GPU 热点，
   `"cpu_time_total"` 看 CPU 侧开销（launch overhead）
3. **profile 本身有开销** —— 不要用 profile 的时间当性能数据，
   它只用来看**占比**和**调用次数**

### CPU 时间 vs CUDA 时间的意义

| 现象 | 含义 |
|---|---|
| CUDA 时间 >> CPU 时间 | GPU 是瓶颈，正常状态 |
| CPU 时间 ≈ CUDA 时间 | **kernel launch 成为瓶颈** |
| CPU 时间 >> CUDA 时间 | 严重的 launch 瓶颈，考虑 CUDA Graph / `torch.compile` |

**Decode 阶段特别容易撞上第二、三种情况**：每个 kernel 只处理 1 个 token，
计算量极小，但 launch 开销固定。几百个小 kernel 的 launch 开销可能超过计算本身。

这是 Day 38 用 `torch.compile` 的核心动机——它能把多个小算子融合，减少 launch 次数。

## 任务 5：Prefill / Decode 热点分析（70 分钟）

Notion 列了六个观察点。逐个做，把结果记进 `notebooks/03_cache_growth.ipynb`。

### 1. Prefill 的大 GEMM

看 `aten::mm` / `aten::bmm` 的输入形状，确认是 `[B*S, D] × [D, *]` 这种大矩阵。
记下它占总时间的百分比。

### 2. Decode 的小 GEMM

同样看 `aten::mm`，形状应该是 `[B, D] × [D, *]`。
**对比两者的「FLOP / 耗时」比值**——Decode 的效率会低得多，
因为小矩阵乘无法打满算力。

### 3. Attention 与 MLP 的时间占比

按模块分组统计。预期：

- Prefill：Attention 占比随 `S` 增长（`S²` 项）
- Decode：MLP 占比更高（参数是 Attention 的 4.2 倍，
  访存密集时时间正比于参数量——Day 11～12 的那个比例现在派上用场了）

**第二条的推理链值得记下来**：Decode 访存密集 → 时间正比于要读的字节数
→ 要读的主要是权重 → MLP 权重是 Attention 的 4.2 倍 → MLP 占大头。

### 4. Cache concat 的复制开销

用 `DynamicCache` profile 一次，找 `aten::cat`。
记下它的总耗时和占比，**再和 `StaticCache` 对比**——
后者应该完全没有 `cat`。

这是 Day 29 那个优化的**直接证据**。

### 5. 预分配是否减少了 allocation / copy

看 profiler 里的 `aten::empty` / `aten::copy_` 调用次数，
以及 `cudaMalloc` 相关条目。`StaticCache` 应该显著更少。

### 6. CPU launch 与 GPU kernel 时间

对比 Prefill 和 Decode 的 CPU/CUDA 时间比。
**Decode 的这个比值应该明显更高**（每个 kernel 干的活少，launch 占比高）。

如果 Decode 的 CPU 时间接近或超过 CUDA 时间，就在笔记里明确写下：
**「Decode 阶段存在 kernel launch 瓶颈」**——这是 Day 38 和
Day 40「下一阶段瓶颈清单」的重要输入。

## 今日最重要的面试式问题

**为什么 Decode 阶段增大 batch 几乎不增加延迟？**

因为 Decode 是**访存密集**的。每层要读全部权重（几十到几百 MB），
而计算只是几个 `[B, D] × [D, *]` 的小矩阵乘。

**权重只读一次，被整个 batch 共享。** batch 从 1 变到 16，
读的字节数几乎不变，计算量虽然 ×16 但本来就不是瓶颈。
所以延迟基本不变，吞吐（tokens/s）近似线性上升。

**这是 continuous batching 的根本依据**——推理服务把并发请求动态凑成大 batch，
吞吐大幅提升而单请求延迟几乎不受影响。

Prefill 相反：它是计算密集的，增大 batch 会线性增加时间。

追问：**Decode 阶段 Attention 和 MLP 谁更耗时？**

**MLP。** 推理链条是：Decode 访存密集 → 时间正比于要读的字节数 →
读的主要是权重 → MLP 参数是 Attention 的约 4.2 倍（`3·D·I` vs `2·D·Dh·(Hq+Hkv)`）
→ MLP 占大头。

注意这和 Prefill 相反：Prefill 时 Attention 有 `S²` 项，长序列下会超过 MLP。
**同一个模型，两个阶段的热点不同**，这是推理优化必须分阶段看的原因。
