## 任务 1：学习 HF 生成策略（30 分钟）

读 Generation Strategies，重点搞清 `GenerationConfig` 里这几个参数的**精确语义**：

| 参数 | 语义 | 容易搞错的地方 |
|---|---|---|
| `max_new_tokens` | **新生成**的 token 数 | 和 `max_length`（含 prompt）不同，后者已不推荐 |
| `do_sample` | 是否采样 | `False` 时 temperature / top-k / top-p **全部无效** |
| `temperature` | 分布尖锐度 | `do_sample=False` 时无意义（Day 3 的结论：单调变换不改排序） |
| `eos_token_id` | 停止 token | 可以是**列表**，任一命中即停 |
| `pad_token_id` | 停止后填充用 | 很多 tokenizer 没有，需要手动指定 |

**`do_sample=False` 时 temperature 无效**这一点，是 Day 3 那条结论的直接推论：
温度是单调变换，不改变 argmax。HF 在这种组合下会给警告，理由就是这个。

## 任务 2：重写 `generate`，支持独立 finished（60 分钟）

Day 4 那版只处理了 `B=1` 或者「整个 batch 一起停」。今天的核心是
**每条序列独立判断结束**。

### 循环骨架

```text
finished = zeros(B, dtype=bool)
for step in range(max_new_tokens):
    logits = model(input_ids)[:, -1, :]        # [B, V]
    next_token = sample(logits)                # [B]
    next_token = where(finished, pad_token_id, next_token)   # 已结束的填 pad
    input_ids = cat([input_ids, next_token[:, None]], dim=1)
    finished |= (next_token == eos_token_id)
    if finished.all():
        break
```

### 四个设计要点

**1. `finished` 是 `[B]` 的布尔张量，不是一个标量。**
不同序列会在不同步结束。用标量等于「有一条结束就全停」，会截断其他序列。

**2. 已结束的序列必须填 `pad`，不能填模型输出。**
模型不知道自己该停了，它会继续产出 token。不覆盖的话结果里会出现 EOS 之后的垃圾。

**3. `finished` 的更新顺序很关键。** 上面代码里
`finished |= (next_token == eos)` 在**拼接之后**——
意思是 EOS 本身**会被保留在输出里**，从下一步开始才填 pad。
这和 HF 的行为一致。如果你先更新 `finished` 再覆盖，EOS 自己就被吃掉了。

**4. `if finished.all(): break` 是纯优化。**
去掉它结果不变（后续都填 pad），但会白算很多轮。加上它，
但要意识到**它让不同输入的实际步数不同**——做 benchmark 时要注意这点。

### `eos_token_id` 支持列表

```python
if isinstance(eos_token_id, int):
    eos_token_id = [eos_token_id]
is_eos = torch.isin(next_token, torch.tensor(eos_token_id))
```

真实模型常有多个终止符（比如 Llama-3 的 `<|eot_id|>` 和 `<|end_of_text|>`），
从一开始就支持列表，省得后面改。

## 任务 3：停止条件测试（30 分钟）

`tests/test_generation.py` 新增：

1. `max_new_tokens=k` 时，输出长度恰好是 `prompt_len + k`
2. `max_new_tokens=0` 时输出等于输入
3. **EOS 被保留**在输出里（不是被 pad 覆盖）
4. EOS 之后**全部是 pad**
5. **独立停止**：构造一个 batch，让第 0 条早停、第 1 条不停，
   验证第 1 条继续生成正常 token
6. `finished.all()` 提前 break 时，输出仍被补齐到统一长度
7. `eos_token_id` 传列表时，任一命中即停

第 5 条是今天最重要的测试。怎么构造？**用受控的假 logits**——
写一个 stub 模型，让它对第 0 条序列在第 2 步输出 EOS、对第 1 条永不输出 EOS。
不要指望随机初始化的真模型碰巧产生你要的行为。

## 任务 4：学习三种采样策略（30 分钟）

### Temperature

```text
softmax(logits / T)
```

Day 3 已学过（见 [`concepts/02-lm-head.md`](./concepts/02-lm-head.md)）。今天补两个实现细节：

- `T` 必须 `> 0`。`T=0` 在数学上是 argmax 的极限，但代码里会**除零**。
  正确做法：`T=0` 时直接走 greedy 分支，不要真的去除。
- `T` 只在采样前作用一次，**不要**在 top-k / top-p 之后再除一遍。

### Top-k

保留 logits 最大的 `k` 个，其余置 `-inf`，然后 softmax 采样。

```python
kth = logits.topk(k, dim=-1).values[..., -1:]     # [B, 1] 第 k 大的值
logits = logits.masked_fill(logits < kth, float("-inf"))
```

注意用 `<` 而不是 `<=`——有并列值时 `<=` 会把并列的都砍掉，可能剩不足 `k` 个。

`k` 要 clamp 到 `[1, V]`。`k > V` 时 `topk` 会报错。

### Top-p（nucleus sampling）

保留**累计概率达到 `p` 的最小集合**。步骤：

```text
1. 按概率降序排序
2. 算累计和 cumsum
3. 找到第一个使 cumsum >= p 的位置
4. 保留到该位置（含），其余置 -inf
```

**关键细节：第一个 token 必须永远保留。** 如果最大概率本身就 `> p`
（比如模型极度确定，`p_max = 0.99`、`p = 0.9`），
按「cumsum >= p 就砍」的朴素写法会**把所有 token 都砍掉**，然后 softmax 全是 NaN。

标准做法是把「是否移除」的掩码**右移一位**：

```python
sorted_probs, sorted_idx = probs.sort(descending=True, dim=-1)
cumsum = sorted_probs.cumsum(dim=-1)
remove = cumsum - sorted_probs > p          # 等价于「移位后的 cumsum > p」
```

`cumsum - sorted_probs` 是「不含当前项的累计和」，第 0 项恒为 0，
所以第 0 项永远不会被移除。**这个技巧要理解，不要背。**

然后用 `scatter` 把掩码映射回原始顺序。

### 三者的适用场景

| 策略 | 场景 | 理由 |
|---|---|---|
| Greedy | 需要确定性输出：代码生成、抽取式问答、评测 | 可复现，无随机性 |
| Top-k | 需要一点多样性，但要可控 | 候选集大小固定，行为可预测 |
| Top-p | 开放式生成：对话、写作 | 候选集**自适应**——模型确定时收窄，不确定时放宽 |

Top-p 优于 top-k 的核心理由就是**自适应**：
top-k 在模型很确定时会强行引入 `k-1` 个不该考虑的候选，
在模型很不确定时又可能砍掉合理选项。

## 任务 5：实现 `sampling.py`（60 分钟）

设计成**可组合的 logits processor 链** + 一个 sampler，
这也是 HF 的结构（Day 25 会正式对照）：

```text
apply_temperature(logits, temperature)  -> logits
apply_top_k(logits, k)                  -> logits
apply_top_p(logits, p)                  -> logits
sample(logits, *, do_sample, generator) -> next_token [B]
```

契约：

- 全部作用在 `[B, V]` 上（不是 `[B, S, V]`——切片在调用方做）
- `temperature <= 0` → `ValueError`（想要 greedy 就传 `do_sample=False`）
- `k <= 0` 或 `p <= 0` 或 `p > 1` → `ValueError`
- `k = None` / `p = None` 表示不启用
- **顺序固定为 temperature → top-k → top-p**，和 HF 一致
- `sample` 接收 `torch.Generator`，**不依赖全局随机状态**

最后一条很重要。用全局 `torch.manual_seed` 的话，
测试之间会互相影响，而且没法在同一进程里做两次独立可复现的生成。
传 `generator` 是干净的做法。

9. **不同种子结果不同**（否则说明 generator 没接上）
10. **分布正确性**：固定 logits 采样 10000 次，

## 今日最重要的面试式问题

**Top-k 与 Top-p 的区别是什么，为什么开放式生成更常用 Top-p？**

top-k 保留固定数量的候选；top-p 保留**累计概率达到 `p` 的最小集合**，
候选数量随模型的确定程度**自适应**。

模型很确定时（比如 `"北京是中国的首"` 之后），top-p 可能只保留 1～2 个候选，
而 top-k 会强行凑够 `k` 个，引入不该考虑的选项。
模型很不确定时，top-p 会放宽到几十个候选，而 top-k 可能砍掉合理选项。

追问：**Top-p 实现里最容易出的 bug 是什么？**

**最大概率本身就大于 `p` 时把所有候选都砍光，导致 softmax 出 NaN。**
修法是把移除掩码右移一位，即用「不含当前项的累计和」判断——
`cumsum - sorted_probs > p`，这样第一个 token 恒被保留。

再追问：**`do_sample=False` 时 temperature 有用吗？**

没用。温度是除以正数，是单调变换，不改变 logits 的排序，
所以不影响 argmax。HF 在这种参数组合下会警告。
