## 任务 1：学习 `inference_mode`（30 分钟）

### 三种模式的区别

| 模式 | 关闭梯度追踪 | 关闭版本计数 | 输出能否用于反向 |
|---|---|---|---|
| 默认 | ✗ | ✗ | 能 |
| `no_grad()` | ✓ | ✗ | 能（作为叶子） |
| `inference_mode()` | ✓ | **✓** | **不能** |

`no_grad` 只是不记录反向图；`inference_mode` **更激进**，
连张量的**版本计数器**（version counter）都不维护。

### 版本计数是什么，为什么它有开销

PyTorch 用版本计数检测「原地修改破坏了反向图」的情况：

```python
x = torch.randn(3, requires_grad=True)
y = x * 2
y.add_(1)          # 原地修改，版本 +1
y.sum().backward() # 如果反向需要 y 的原值，PyTorch 会报错
```

维护它的代价是**每个张量操作都要更新元数据**，还要在读取时检查。
单次开销很小，但推理循环里有成千上万次操作，累积起来可观。

`inference_mode` 下创建的张量**根本没有版本计数器**，
所以省掉了这部分开销，也省了一点内存。

代价：这些张量**永久不能参与 autograd**。就算之后退出了
`inference_mode` 上下文也不行。纯推理项目里这不是问题。

### 预期收益有多大

**不要期待很大。** 版本计数的开销主要在 **CPU 侧**——
它影响的是 Python/C++ 层的 bookkeeping，不影响 GPU kernel。

所以：

- **小模型 / Decode 阶段**（CPU 开销占比高）→ 收益可能有几个百分点
- **大模型 / Prefill 阶段**（GPU 时间支配）→ 收益接近 0

这个预判很重要——**如果你测出 30% 的提升，那大概是测量方法有问题**
（比如忘了 warmup，或者默认模式那次多了建反向图的显存分配）。

### 顺手检查一个真实风险

`inference_mode` 下产生的张量不能参与 autograd。
如果你的代码里有任何地方要对推理输出做梯度操作（比如做 saliency 分析），

## 任务 3：SDPA 后端对照（60 分钟）

`F.scaled_dot_product_attention` 有多个后端，PyTorch 会自动选。今天手动指定来对比。

```python
from torch.nn.attention import sdpa_kernel, SDPBackend

with sdpa_kernel(SDPBackend.MATH):
    out = F.scaled_dot_product_attention(q, k, v)
```

### 四个后端

| 后端 | 特点 | 限制 |
|---|---|---|
| `MATH` | 朴素实现，实体化 `[B,H,Sq,Skv]` | 无限制，任何情况都能用 |
| `FLASH_ATTENTION` | FlashAttention，不实体化 | 需要 fp16/bf16、特定 `Dh`、GPU 架构 |
| `EFFICIENT_ATTENTION` | 内存高效实现 | 限制较少 |
| `CUDNN_ATTENTION` | cuDNN 实现 | 需要较新 cuDNN |

### 对照矩阵

对每个可用后端 + 你自己的 `naive_attention`，测：

| 维度 | 取值 |
|---|---|
| `S` | 128, 512, 1024, 2048, 4096 |
| dtype | fp32, bf16 |

记录：latency、峰值显存。

### 核心观察

**1. 显存随 `S` 的增长阶数不同。**

```text
naive / MATH        显存 ~ S²      （实体化注意力矩阵）
FLASH / EFFICIENT   显存 ~ S       （分块计算）
```

**画成对数-对数图，斜率就是阶数。** 这是今天最有说服力的一张图——
斜率 2 vs 斜率 1 一目了然。

**2. fp32 下 FlashAttention 不可用。** 它要求 fp16/bf16。
所以 `sdpa_kernel(SDPBackend.FLASH_ATTENTION)` 在 fp32 下会报错或回退。
**这是「为什么推理用 bf16」的一个具体理由**——不只是省显存，
还能解锁更快的 kernel。

**3. 数值差异。** 不同后端的浮点累加顺序不同，结果有细微差异。
**验证一下：各后端之间的最大误差是多少？** 
和 Day 30 那个「浮点重排」的量级应该一致（`~1e-6` in fp32）。

如果某个后端的误差明显更大（比如 `1e-3`），说明它内部用了更低精度累加——
这是个值得记录的发现。

### 在 CPU 上

只有 `MATH` 可用。测你的 `naive` vs `MATH` 的差异即可，
在笔记里标注「FlashAttention 相关结论待 GPU 验证」。

## 任务 4：`torch.compile` 对照（60 分钟）

```python
compiled = torch.compile(model)
```

一行，但有三个必须测的东西。

### 1. 冷启动代价

第一次调用会触发编译，可能要**几十秒到几分钟**。

```text
第 1 次调用   编译 + 执行     ← 记录这个时间
第 2 次起     只执行          ← 记录稳态时间
```

**报告里必须同时给出这两个数字。** 只报稳态性能是不诚实的——
对于短命的进程，编译时间可能永远赚不回来。

算一下**回本点**：`编译时间 / 每次节省的时间 = 需要跑多少次才划算`。

### 2. 重编译问题（今天的重点）

`torch.compile` 按**输入形状**编译。形状变了就重新编译。

```text
DynamicCache   每轮 Skv 都变 → 每轮可能重编译 → 灾难性地慢
StaticCache    形状固定       → 编译一次复用   → 这才是它的价值
```

**这就是 Day 27 那句「`StaticCache` 是 `torch.compile` 的前提」的实证。**
今天亲眼看一遍：

```python
torch._logging.set_logs(recompiles=True)     # 打开重编译日志
```

用 `DynamicCache` 跑生成，看日志里刷出多少次重编译。
再用 `StaticCache` 跑，应该只编译一两次。

**这个对比是今天最重要的实验**，一定要做。它把 Day 29 那个优化
从「省点拷贝」升级成「解锁编译」。

### 3. Prefill vs Decode 的收益差异

预期：

| 阶段 | 收益 | 为什么 |
|---|---|---|
| Prefill | 小 | 已经是大 GEMM，算子融合空间有限 |
| **Decode** | **大** | 一堆小算子，融合能显著减少 kernel launch |

Day 34～35 如果测出「Decode 有 launch 瓶颈」，这里应该能看到明显改善。
**这两天的结论要串起来**。

### 4. 数值一致性

编译后结果可能有细微差异（算子融合改变了运算顺序）。

```python
torch.testing.assert_close(compiled(x), model(x))
```

**如果差异超过 Day 30 记录的浮点噪声量级，要在报告里明确指出。**
编译带来的数值变化是真实存在的工程风险。

### 可能遇到的问题

`torch.compile` 在某些代码模式下会 graph break（回退到 eager）或直接报错。
常见触发点：Python 控制流依赖张量值、`.item()` 调用、动态形状。

```python
torch._logging.set_logs(graph_breaks=True)
```

**如果有 graph break，记录在哪里断的**——这本身是个有价值的发现，
说明你的代码有对编译不友好的地方（很可能就是那些 `.item()`，Day 34 提过）。

如果完全跑不通，记录报错信息，在笔记里写「已知限制」，别硬磕。

## 今日最重要的面试式问题

**`torch.compile` 为什么需要固定形状的 KV Cache？**

因为 `torch.compile` 按**输入形状**编译并缓存图。形状变化会触发**重编译**。

`DynamicCache` 每轮 `Skv` 都增长（`S → S+1 → S+2`），
意味着每一步都是新形状，可能每步都重编译——编译开销远超执行收益，**反而更慢**。

`StaticCache` 预分配到 `max_seq_len`、形状恒定，编译一次就能复用整个生成过程。

这也是 CUDA Graph 的前提条件，原因相同。

追问：**`torch.compile` 对 Prefill 和 Decode 哪个收益更大？**

**Decode。** Prefill 已经是大 GEMM 主导，算子融合的空间有限。

Decode 是一堆小算子，每个 kernel 只处理 1 个 token，
**kernel launch 开销占比很高**。编译后的算子融合能显著减少 launch 次数，
所以收益大得多。

追问：**`inference_mode` 比 `no_grad` 快多少？**

**通常只有几个百分点，甚至测不出来。** 它省的是**版本计数**的维护开销，
那是 CPU 侧的 bookkeeping，不影响 GPU kernel。

它的主要价值其实是**显存**（不保存反向所需的中间量）和**代码意图清晰**。
如果谁声称它带来了几十个百分点的加速，大概是测量方法有问题。
